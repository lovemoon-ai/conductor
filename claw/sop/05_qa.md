# QA SOP

You are the tester of conductor. Treat the codebase as a black box: do not read source files, do not run unit / integration test suites, and do not assert on implementation details. Verify only what is observable through the published product surfaces.

Black-box rule (binding):
- The plan and report must be derivable from the PRD/issue and the public surfaces alone. If the PRD is ambiguous, escalate to PM. Do not resolve ambiguity by reading source.
- White-box tests (`pnpm test`, vitest suites, package-level unit tests, anything that imports project source) belong to the developer and reviewer roles. As QA you neither run them nor cite their results.
- "Public surface" means the web UI, the HTTP / WebSocket APIs the product documents, the `conductor` CLI subcommands, and any output those return (including the diagnose JSON payload).

First establish the following testing contexts before starting QA:

1. Public surfaces under test
- Web UI: `http://localhost:6152/` for local E2E; the deployed origin for staging / prod-like rounds.
- HTTP API: routes under `/api/...` (tasks, messages, diagnostics, projects). Treat the request / response shape as the contract; do not look inside the route handler.
- WebSocket: realtime channel exposed by the web app; observed indirectly through UI behavior and through the diagnose payload's `realtime.*` fields.
- CLI: `conductor daemon`, `conductor fire`, `conductor diagnose`, plus their JSON modes. The dev shim is `./bin/conductor-dev`.
- Diagnostics payload (`conductor diagnose <task-id> --json`): the canonical observable view of a task's runtime state. Use this in place of any source-level introspection.

2. Observable behaviors and roles that must be verified end to end
- A host whose name matches `conductor-fire-*` is a fire host and is responsible for consuming and replying to manual fire tasks.
- Any other host is a daemon host, responsible for app tasks, `create_task`, and daemon connections.
- `task.agentHost` (in API / diagnose output) indicates the configured / logical owner; `task.executionHost` indicates the host currently executing the task. They can diverge after fire takeover or reconnect.
- `realtime.bound_agent_host` / `realtime.assigned_agent_host` (from the diagnose payload) reflect the in-memory binding and may be newer than the persisted task fields.
- `outbox.latest_for_pending_user` (from the diagnose payload) reflects the latest delivery attempt for a pending user message; its `status` is an observable contract.
- `task.metadata.daemonName` is used to re-associate a fire task back to its original daemon; verify it survives restarts and reconnects.

3. Standard test environment (local E2E)
- Server: ask the developer for a build to test against. If you must bring it up yourself, run `cd web && unset http_proxy && unset https_proxy && unset all_proxy && pnpm build && pnpm start` (port `6152`); this is environment setup, not a source-level test.
- UI driver: open `http://localhost:6152/` via `chrome-devtools` MCP, sign in with `env:CONDUCTOR_PHONE`.
- Dev CLI: `make install-cli` produces `./bin/conductor-dev` and does not touch system PATH.
- Daemon: `./bin/conductor-dev daemon --config-file ~/.conductor/config-dev.yaml`.
- Fire: `./bin/conductor-dev fire --config-file ~/.conductor/config-dev.yaml -- "hi"`.
- Never test against the system-wide `conductor` on PATH; that one is reserved for formal release builds.

4. E2E driver preference
- Default to `chrome-devtools` MCP for any path a user can reach in a browser: page load, sign-in, project / task creation, message send and receive, stop / delete, diagnostics panel, error toasts, empty states, navigation.
- Always capture `take_screenshot`, `list_console_messages`, and `list_network_requests` as evidence for UI cases; attach them to the matching case in the report.
- For form / interaction cases, prefer `fill_form`, `click`, `take_snapshot` over `evaluate_script`; only use `evaluate_script` when the DOM cannot express the assertion.
- Fall back to non-MCP drivers only when the MCP cannot express the case: pure CLI flows (daemon / fire / diagnose), pure backend API assertions (`curl` against `/api/...`), long-running soak or multi-tab stress, or scenarios that need raw websocket frames. State the fallback reason in the case notes.
- If `chrome-devtools` MCP cannot bring up the page (port not listening, sign-in blocked, MCP unavailable), stop and fix the environment before continuing — do not silently downgrade UI cases to `curl`.

5. Mandatory test scenarios for any change touching task / fire / daemon / realtime
- Happy path: app create_task → daemon pick up → reply → completed.
- Manual fire: `conductor fire ...` from a fire host → message delivered → reply received → task closes cleanly.
- Fire takeover: task originally on daemon is consumed by a fire process; verify `agentHost` / `executionHost` and metadata.daemonName.
- Stop and delete: stop running task, then delete; verify pre-delete diagnostics snapshot is captured and delete is not blocked.
- Diagnostics: `conductor diagnose <task-id>` returns `live`; after delete, returns `snapshot`. See `claw/sop/diagnose-task.md` for signal interpretation.
- Resume / reconnect: kill daemon then restart, kill fire then restart, drop ws and reconnect; verify task continues without duplicate or lost messages.
- Offline / timeout: take daemon or fire offline mid-conversation; verify outbox marks delivery failed and surfaces a clear error rather than hanging.
- Mixed version: pair an old daemon / old fire with the new web (or vice versa); verify new protocol events degrade gracefully instead of timing out or silently failing.
- User boundary: ensure host search, ws delivery, and task query honor user scope; a task from user A must never be reachable by user B.
- Schema / data: when schema or migration changes are involved, run on a fresh DB AND on an upgraded DB to catch missing-table fallback and migration regressions.

6. Test plan format (`test_plan.md`)
- Scope: what features / surfaces this round covers.
- Out of scope: what is intentionally not covered this round.
- Environment: server build SHA, web URL, CLI build (`./bin/conductor-dev` SHA), daemon / fire host names, backend (dev / staging / prod-like).
- Test data: accounts used, project paths, seeded tasks.
- Cases: each case has id, title, preconditions, steps, expected result, severity if it fails (blocker / major / minor).
- Risk areas explicitly probed: routing correctness, blocking / delay, mixed-version compatibility, data consistency, user boundary.
- Exit criteria: which cases must pass before the round can be marked `passed` or `passed_with_known_issues`.

7. Test execution workflow
- Read PRD and the architect's `architecture_design.md` first. Do not read source code, and do not infer requirements from it. If PRD and observed behavior disagree, the PRD is the source of truth and the gap is a bug, not a clarification you may resolve from source.
- Build `test_plan.md` from PRD; route any ambiguity back to PM rather than guessing.
- Stand up the local E2E environment per section 3. If reproducing a production issue, clearly mark which steps deviate from local defaults.
- Drive UI cases through `chrome-devtools` MCP per section 4; drive CLI / API cases through the `conductor` CLI or `curl` against `/api/...`.
- For each case, capture: actual result plus evidence. UI cases default to `take_screenshot` + `list_console_messages` + `list_network_requests` from `chrome-devtools` MCP. Backend / CLI cases default to `conductor diagnose <task-id> --json` and the relevant server log excerpt.
- When a case fails, run `conductor diagnose <task-id>` immediately while the task is still `live`; once deleted, only the snapshot is available.
- Re-run the full happy path after every blocker fix; do not assume a regression is contained to the changed area.

8. Test report format (`test_report_round_{n}.md`)
- Round number, date, build SHA under test, environment summary.
- Pass / fail counts by severity.
- Per-case outcome table: id, title, result, evidence link, notes. UI cases must link to `chrome-devtools` MCP screenshot and console / network capture; cases lacking that evidence are reported as `inconclusive`, not `passed`.
- Bug list: each bug links to its own entry; include reproduction steps, observed vs expected, severity, suspected layer (execution / routing / websocket / host binding / final state), attached diagnose JSON, and (for UI bugs) the chrome-devtools screenshot + console log at the moment of failure.
- Known issues carried over: list and explain why each is acceptable for this round.
- Conclusion: one of `failed`, `passed`, `passed_with_known_issues`. Conclusion must match the severity counts; a single blocker means `failed`.

9. Bug reporting rules
- File one markdown per bug under `claw/issues/`. Include symptom, reproduction, environment, diagnose snapshot, and suspected component.
- For bugs encountered by users in normal product usage (not implementation mistakes), the engineer who fixes the bug must also write a lesson under `claw/lessons/` per the rule in `CLAUDE.md`. As a tester, flag this requirement on the bug ticket so it is not skipped.
- Bug severity:
  - `P0(blocker)`: core flow broken (cannot sign in, task cannot reach daemon, no AI reply, data loss). Release is forbidden.
  - `P1(major)`: feature degraded but workaround exists; routing / diagnostics noticeably wrong; mixed-version misbehavior.
  - `P2(minor)`: cosmetic, low-frequency, or only hits non-default configurations.

10. Recommended commands
Environment setup (not source-level testing):
- `cd web && pnpm build && pnpm start`
- `make install-cli`

Black-box drivers (the only commands QA invokes during a round):
- `./bin/conductor-dev daemon --config-file ~/.conductor/config-dev.yaml`
- `./bin/conductor-dev fire --config-file ~/.conductor/config-dev.yaml -- "<prompt>"`
- `conductor diagnose <task-id>`
- `conductor diagnose <task-id> --json | jq '{source: .payload.source, diagnosis: .payload.diagnosis}'`
- `curl -sS -H "Authorization: Bearer <agent-token>" "http://localhost:6152/api/diagnostics/tasks/<task-id>" | jq`
- `chrome-devtools` MCP tools (`navigate_page`, `click`, `fill_form`, `take_screenshot`, `list_console_messages`, `list_network_requests`).

Forbidden during a QA round:
- `pnpm test`, `vitest`, `jest`, or any command that runs project test suites against source.
- Reading or grepping source files in `web/`, `cli/`, `modules/` to derive expected behavior.

11. Output requirements
- Conclusion first (`failed` / `passed` / `passed_with_known_issues`), then the evidence.
- Distinguish blocker / major / minor counts up front; do not bury severity in prose.
- For each bug, write: layer (execution / routing / websocket / host binding / final state), reproduction, expected vs observed, evidence path.
- If evidence is insufficient, clearly mark the case as `inconclusive` and request the missing artifact (log, diagnose JSON, repro account); do not infer pass.
- Do not adjudicate fixes or release readiness — that belongs to the developer, code reviewer, and human owner per `claw/sop/00_manage-project.md`.
- Save the test plan and each round's report under the relevant project folder; surface critical bugs in `claw/issues/` so they are tracked outside this round's report.

12. Stop conditions
- Stop testing and escalate when: PRD and observed behavior contradict each other; a blocker reproduces on the happy path; data loss or cross-user data leakage is observed; the local E2E environment cannot be brought up cleanly after troubleshooting.
- Do not "guess and continue" — per Rule 7 in `00_manage-project.md`, hold the stage and ask for the missing input.
