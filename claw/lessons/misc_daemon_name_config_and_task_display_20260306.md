# misc: review of inconsistent daemon_name configuration and task display (2026-03-06)

## Symptoms
- When users access the Desktop daemon according to web configuration or documents, they are likely to encounter name configuration inconsistencies:
- There is no `daemon_name` in the configuration generated by `conductor config`
- `conductor daemon` still relies on the command line `--name`
- The task list in the app only displays the general `fire` for manual fire tasks, and the actual device name cannot be seen.
- The result on the user side is:
- Desktop daemon naming is scattered in config, CLI parameters and UI inference
- When multiple machines are online at the same time, it is difficult to confirm which device the current task is running on.

## Root Cause
- The old implementation did not treat the "human-readable daemon display name" as a separate field throughout the system.
- `agentHost` / `executionHost` takes on the three responsibilities of routing, attribution, and display at the same time. The frontend can only guess whether it is fire through the host prefix.
- Configuration generation, daemon startup, SDK creation tasks, and front-end display each use different sources, resulting in name semantic drift.

## Fix
- `daemon_name` is officially introduced in `~/.conductor/config.yaml`, and the local hostname is taken by default.
- `conductor daemon` is changed to read `daemon_name` from the configuration, `--name` is no longer required.
- When fire creates a task, write `daemon_name` into the task metadata, keeping it only as a display tag and not participating in routing.
- Updated the web configuration interface, Getting Started document and task list display logic, giving priority to the daemon name in runtime/metadata.
- Add CLI, SDK, and frontend testing to ensure that configuration reading, task writing, and UI display are consistent.

## Prevention
- Route identifiers and display names must be modeled separately, and you cannot continue to rely on the host prefix to infer UI copy.
- Any user-visible field must ensure that the semantics of "configuration entry, back-end persistence, and front-end display" are consistent.
- When a field is only used for display, it should be explicitly put into metadata or a dedicated column to avoid reuse with ownership / routing fields.
